# ReceiptOS Verify v0.2 vector and mutation witnesses

This review accounts for all **38 new static vectors** (`G01`-`G30`, `I01`-`I08`) and all **14 semantic mutants** (`M01`-`M14`). The original 30 v0.1 vectors remain a separate regression corpus, giving 68 combined vectors. Counts describe cases and catalog entries; they do not imply 38 independent relations or exhaustive security coverage.

The inputs are the checked-in `vectors/v0.2/<ID>.json` files, not dynamically generated expected outputs. `tools/generate-v02-vectors.mjs` records literal expected projections, 14 layer statuses, selected native values and required reason codes. It never calls `verifyV2`, `projectV2` or an adapter to calculate the expected product verdict. This document reads those literal expectations and the recorded results; it is not a second implementation of the verifier.

## Oracle origins and limits

| Oracle family | Origin of the literal expectation | Independence and evidence boundary |
| --- | --- | --- |
| O-GEN/RVR | Human-selected equality/inequality, dependency, applicability and evidence-presence premises in `tools/generate-v02-vectors.mjs`, plus the literal SHA256 predicate of a fresh synthetic artifact. | Product expectations are detached from verifier output. Fixture construction still shares canonicalization, signing and surface-extraction utilities with production; this is not an independently implemented canonicalizer, signer or schema oracle. RVR's saved artifact is generated native evidence, not the product expectation. |
| O-GEN/SABI | Literal compatible/incompatible semantic declaration and literal native pair expectation; unchanged public neutral linker executes at its pinned source. | Product JSON strings encode native v0 claim/scope/time fields. Subject, artifact, authority ID, policy, version and dependency checks remain product relations. `observedSemanticPair=PRESERVED` does not mean the full generic surface is compatible. Native pair grading uses no expected pair invented from its own observed result. |
| O-KIT | `tests/helpers/trustless-v02-fixture.mjs` contains independent literal positive, poison-negative and opaque-scanner outcomes; one-leaf Merkle construction is independent of the native checker. Actual unchanged checker CLI generates saved artifacts. | The adapter reruns the checker and main runner; saved expectations serve only as replay targets. Runner PASS can reproduce a negative result. The deliberately narrow toy scanner is not a poisoning-absence proof or full recompute-kit conformance. Opaque scanner authentication is not scanner execution. |
| O-ACTION | Explicit synthetic up intent and separate caller-selected action; exact material identity, attempt, observation and duplicate premises are selected literally. Native upstream Schnorr verification executes. | Fixture construction uses product `actionMaterial` and `commitActionTrace`; therefore correct construction of the trace commitment is not independently proved by this corpus. Fresh synthetic key control and a supplied trace do not establish real Interpoll admission, server execution, freshness or a deployed actor identity. |
| O-PRF | Literal finalized award/accepted matching settlement, amount 50, native PRESERVED result, missing-settlement UNVERIFIABLE result and two independently caller-accepted dependency identities. Unchanged native main relation executes on the selected tuple. | The dependency basis is caller-accepted, not discovered or proven complete by this adapter. The guarantee concerns the separately selected award/settlement tuple and transfer relation; it does not silently become a guarantee about the surrounding RVR claim. Open PR14 informs the experimental product transfer relation, not main-source behavior or wire compatibility. |

All fixtures are synthetic. The same project authors selected the relations and literals; there is no claim of organizationally independent audit authorship. Native source execution supplies an additional executable comparison where described, not an independent proof of every wrapper decision.

## Literal expectation convention

Every vector explicitly stores all 14 expected layer statuses. The common base is:

| Layer | Literal base status |
| --- | --- |
| INPUT | `ADMITTED` |
| CANONICALIZATION | `VERIFIED` |
| INTEGRITY | `VERIFIED` |
| AUTHENTICITY | `VERIFIED` |
| SUBJECT_BINDING | `VERIFIED` |
| RECOMPUTATION | `REPRODUCED` |
| EVIDENCE_SUFFICIENCY | `SUFFICIENT` |
| SEMANTIC_COMPATIBILITY | `COMPATIBLE` |
| GUARANTEE_PRESERVATION | `NOT_REQUESTED` |
| CONTINUITY | `NOT_REQUESTED` |
| DOMAIN_ADAPTERS | `NOT_REQUESTED` |
| PRODUCT_PROJECTION | `VERIFIED` |
| EXPLAINABLE_REPORT | `GENERATED` |
| PROVENANCE | `RECORDED` |

The following matrix lists every deviation from that base and every required reason. `PRODUCT_PROJECTION` always equals the literal overall result. Unlisted layer statuses retain the table above. `R` means `RECOMPUTATION.semanticOutcome`; `Pair` means `SEMANTIC_COMPATIBILITY.observedSemanticPair`. `runner`, `scan`, `signature`, `grade` and `PRF upstream` are the selected literal native keys, not Boolean aliases for overall verification.

Reason checks require the listed codes to be present. They do **not** lock the complete reason array or forbid additional diagnostic reasons. Native-key checks likewise select explicit paths rather than independently validating every byte of the complete native report; strict report admission and adapter-specific tests provide separate controls.

## Overlap, control selection and metadata corrections

- `G13`/`I01` are exact request/bundle aliases, and `G14`/`I05` are exact request/bundle aliases. They preserve the requested general/domain listings, but contribute two positive/negative scenarios, not four independent scenarios.
- `G04`/`G19` differ only in the mismatching authority ID value and exercise the same authority branch. The measured M01 witness is G04.
- `G01`/`G09` share the artifact replay relation and global Semantic ABI evaluation. G09 additionally exercises the semantic-abi selector route; it is not another independently implemented content verifier.
- `G05`/`G10` share exact-scope rejection and neutral linker failure, using different literal scopes and adapter selector labels. Only G05 is the measured M02 witness.
- `G11`/`G18` both exercise claim mismatch. Their mutation controls differ: native Trustless positive bypass (M07) versus integrity/signature bypass (M12). This is overlapping defense coverage against distinct projection defects.
- `G02`, `G03`, `G22` and `G25` change different identity dimensions; they are not four independent native verifiers. `I02`/`I03` likewise exercise different material action fields through the same equality branch.
- `G07`/`G08` now name G23, the satisfied dependency premise, as their positive control in both static metadata and the generator. This corrected metadata only; request, bundle and literal expectations were unchanged. G10's misleading M02 annotation was removed; the relation remains covered. Metadata associating G19 with M01 and I05 with M09 is a defect association, not an additional recorded mutation execution.
- G14/I05 were strengthened from changing the sole attempt to changing a real **second** pending retry after an unchanged accepted/executed first attempt.
